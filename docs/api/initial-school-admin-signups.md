# 최초 학교관리자 가입·미등록 학교 신청

계정 정보와 학교명·홈페이지·담당자 정보를 함께 접수한다. **계정·신청·세션은 하나의
트랜잭션으로 저장**하며 승인 전 계정은 `user` 권한이다. 제안 학교는 공식 학교 목록에
자동 등록하지 않는다. 기존 일반 가입 및 등록 학교 UUID 기반 권한 신청 계약은 유지한다.

## 최초 가입과 재시도

`POST /api/v1/auth/school-admin-signups`는 기존 가입의 `display_name`, `email`,
`password`(15~128자), `session_mode`와 아래 신청 정보를 받는다.

| 필드 | 계약 |
|---|---|
| `client_id` | 제출·결과 유실 재확인 동안 유지할 UUID |
| `school_name` | 필수 1~128자, 앞뒤 공백 제거·NFC, 제어문자 금지 |
| `official_url` | 선택, 최대 2048자, 인증정보 없는 HTTP(S) URL, 서버가 가져오지 않음 |
| `position` | 직책, 필수 1~128자 |
| `contact_email` | 연락 이메일, 정규화, 최대 254자 |
| `reason` | 신청 사유, 필수 1~1000자 |

성공은 201이며 기존 로그인 응답에 `signup` 접수 상세를 추가한다. Web은 기존 Secure
HttpOnly 쿠키, Windows는 메모리 Bearer를 사용한다. 권한·owner·학교 ID·승인 상태를
요청에서 정할 수 없다. 연락 이메일·홈페이지 입력은 소속 확인을 대신하지 않는다.

같은 이메일·client_id의 재확인은 신청 정보·가입 이름·현재 비밀번호를 검증한 뒤 같은
계정과 접수를 반환한다. 세션 토큰은 새로 발급할 수 있다. 반려·승인·취소 이력은 재시도로
되살리지 않는다. 다른 정보로 같은 키를 사용하거나 이미 가입된 계정에 새 최초 접수를
붙이려 하면 409다. 원문 비밀번호나 비밀번호의 단순 지문은 신청에 저장하지 않는다.

기존 가입과 이메일별 15분 3회 한도를 공유한다. 공개 앱 프록시의 IP별 가입 한도도
공유한다. 쿠키 Origin 검증·정지 계정 제한·공통 오류·no-store 정책을 유지한다.
응답 유실은 실패나 성공으로 단정하지 않는다. 프론트는 같은 요청 ID와 입력으로 재확인하거나
로그인한 뒤 이력을 조회한다. 접수 확인 후 번호와 승인 대기를 표시하고 계속하기로 진입한다.

## 로그인한 신청자

prefix는 `/api/v1/me/school-admin-signups`다.

| 메서드·경로 | 동작 |
|---|---|
| `GET {prefix}` | 본인 최초·미등록 학교 신청 이력 |
| `POST {prefix}` | 기존 계정의 미등록 학교 신청. 위 신청 정보만 사용 |
| `GET {prefix}/{id}` | 본인 상세. 다른 계정 UUID는 404 |
| `POST {prefix}/{id}/cancel` | `expected_version`으로 대기 신청 취소 |

본인/client_id UNIQUE, 본인/학교명의 NFC·casefold 키별 대기 신청 UNIQUE다. 학교명 키는
중복 접수를 제한할 뿐 공식 학교 ID를 추론하지 않는다. 대기 최대 5개·이력 최대 100개이며
등록 학교 권한 신청과 별도 보관한다. 취소·반려 후 보완 신청은 새 client_id를 사용한다.
취소·반려는 계정이나 개인 자료를 삭제하지 않는다. 목록은 상태 필터, UUID cursor,
limit(1~100, 기본 30), `items/next_cursor`를 제공한다.

## 슈퍼관리자 승인·반려

prefix는 `/api/v1/admin/school-admin-signups`다. GET 목록·GET `/{id}`·POST
`/{id}/approve`·POST `/{id}/reject`를 제공한다. 목록/상세는 슈퍼관리자만 접근한다.
승인에는 신청 `expected_version`, 현재 신청자 `expected_user_version`, 신청자에게 보이는
`review_note`(1~500자), 각각 엄격한 boolean true인 `identity_verified`,
`affiliation_verified`와 다음 두 방식 중 **하나만** 필요하다.

- 기존 학교 연결: `institution_id`와 검토한 `expected_institution_version`.
- 새 학교 등록: `new_institution`에 `name`, 선택 `official_url/country_code`.

기존 학교의 보관·버전 변경, 정지/슈퍼관리자로 변경된 신청자, 이미 부여된 같은 학교
범위, 동시 처리·오래된 신청 버전은 409다. 같은 이름의 학교를 새로 만들려 해도 409이며
기존 학교를 확인해 명시적으로 연결해야 한다. 자동 병합·자동 소속 인증은 하지 않는다.

현재 신원 잠금 안에서 신청 승인·필요한 학교 등록·school_admin 역할·해당 학교 전체
범위·권한 버전·최소 감사를 함께 커밋한다. 일부 저장에 실패하면 모두 롤백한다.
신청은 `pending → approved/rejected/cancelled`로만 전이한다. 과거 승인 이력과 현재
접근 권한은 구분하며 실제 권한은 `/auth/me` 및 보호 API가 다시 판단한다.

슈퍼관리자 접수 화면의 `최초·미등록 학교 접수`에서 심사하고, 등록 학교 권한 신청 탭은
기존 API를 사용한다. 심사는 입력 보호가 있는 대화상자에서 진행한다. 충돌/응답 불명은
재승인을 잠그고 `심사 결과 다시 확인`으로 현재 상태를 읽는다. 401/403이나 계정 변경은
신청자 개인정보와 심사 제어를 숨긴다. 학교 SSO·메일 인증·첨부 증빙·메일 알림은 별도다.

`0014_school_admin_signups`는 비공개 신청 테이블 하나를 추가한다. 기존 마이그레이션과
기존 학교·계정·학생 자료를 다시 쓰지 않는다. 학사 문서·학생 기록·졸업감사·RAG의
공식 검토 계약과도 별개의 절차다.
