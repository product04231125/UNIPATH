# 학교관리자 가입 신청·승인 API

2026-11-04: 아래 **목표 계약(미구현)** 은 백엔드 런타임·OpenAPI에 아직 반영하지 않은
제품 계약이다. **현재 구현** 은 2026-10-23 서버 동작이다. 구현 전까지 클라이언트는
현재 구현을 따른다. 최초·미등록 학교·첫 학교관리자는
[최초 가입 계약](initial-school-admin-signups.md)을 본다.

## 목표 계약 (미구현)

학생 계정과 학교관리자 계정은 신청으로 섞지 않는다. 일반 이메일로 학생 가입·로그인한 뒤
학교 관리 권한을 신청하는 경로는 닫는다. 추가 학교 인력은 학교관리자 가입으로만 들어오고,
심사는 **그 학교에 이미 있는 `school_admin`** 이 한다. 슈퍼는 미등록 학교와 그 학교의
**첫** 학교관리자, 정지·강제 회수·감사만 필수 담당한다.

### 학생 계정 생성 거부

`POST /api/v1/me/school-admin-applications`와 `POST /api/v1/me/school-admin-signups`는
역할이 `user`이면 생성하지 않는다. 세션이 있어도 403이며, 클라이언트가 메시지 문자열을
파싱하지 않도록 전용 코드를 쓴다.

| 항목 | 목표 |
|---|---|
| HTTP | 403 |
| `error.code` | `STUDENT_SCHOOL_ADMIN_APPLY_FORBIDDEN` (구현 시 `ErrorCode`에 추가) |
| 본문 | 공통 envelope. 신청을 만들지 않음 |
| 조회·취소 | 본인에게 과거 이력이 있으면 GET/cancel은 유지할 수 있으나 새 생성은 거부 |

슈퍼관리자는 지금처럼 새로 신청하지 않는다. 이미 `school_admin`인 계정이 **다른 등록
학교**의 범위를 더 받으려 할 때만 `POST /me/school-admin-applications`를 허용한다.
그 심사는 대상 학교의 기존 `school_admin`이다. 활성 범위가 아직 없는 학교는 첫 관리자
경로이므로 이 API가 아니라 [최초 가입](initial-school-admin-signups.md)이다.

추가 인력의 기본 진입은 공개 `POST /auth/school-admin-signups`다. 대상 학교에 활성
학교관리자가 있으면 그 접수를 아래 검토 API의 추가 신청으로 본다. 조교 전용 하위 역할은
없으므로 승인 결과는 항상 `school_admin` + 해당 학교 전체 범위다.

### 기존 학교관리자 검토 (슈퍼 전용 승인에서 변경)

prefix는 `/api/v1/admin/school-admin-applications`를 유지한다. **학교관리자도 자기
학교 범위 안에서 이 경로에 접근한다.** 목록·상세·승인·반려가 다른 학교 신청을 보여
주거나 처리하면 403/404다(다른 사람 UUID와 같은 숨김 정책).

| 메서드·경로 | 목표 |
|---|---|
| `GET {prefix}` | 본인 활성 범위 학교의 추가 신청만. 상태·학교·cursor 필터 |
| `GET {prefix}/{id}` | 같은 학교 신청과 신청자 계정·권한 버전 |
| `POST {prefix}/{id}/approve` | 추가 관리자 승인. 학교 전체 범위 부여 |
| `POST {prefix}/{id}/reject` | 대기 추가 신청 반려. `review_note`는 신청자에게 보임 |

승인 입력은 현재와 같이 `expected_version`, `expected_user_version`, `review_note`(1~500자),
`identity_verified`/`affiliation_verified` true다. 학교관리자가 자기 학교 담당자 자격을
확인했다는 기록이며, 시스템이 이메일을 자동 증명했다고 표시하지 않는다.

학교관리자 승인은 **추가** 인력만 처리한다. 아래는 409다.

- 대상 학교에 활성 `school_admin` 범위가 아직 없음(첫 관리자 → 슈퍼의 signup 승인)
- 미등록 학교·공식 학교 ID 없는 신청
- 신청자 역할이 이미 `super_admin`이거나 정지
- 이미 같은 학교 활성 범위가 있음
- 자기 자신의 신청

승인 트랜잭션은 현재와 같다: 신청 승인·`school_admin` 역할·학교 전체 범위·권한 버전·
감사를 한 번에 저장하고 실패 시 롤백. 신청자를 학생(`user`)으로 두거나 되돌리지 않는다.
반려도 학생 전환이 아니다.

슈퍼관리자는 같은 경로로 추가 신청을 처리할 수 있으나, 일상 심사 주체는 해당 학교
`school_admin`이다. 슈퍼 전용으로 남는 것은 미등록 학교·첫 학교관리자, 계정 정지,
강제 범위 회수, 감사 조회다. 범위 부여/회수 목표는 [인증 API](authentication.md)를 본다.

`pending → approved/rejected/cancelled`만 허용한다. 현재 권한은 `/auth/me`와 보호 API가
판단한다. 첨부 증빙·메일 알림·학과 하위 범위·조교 역할은 이 계약 밖이다.

## 현재 구현

2026-10-23 구현. 일반 이메일 계정으로 가입·로그인한 뒤 학교 관리 권한을 신청한다.
기존 로그인·개인 자료는 유지한다. 신청 자체로 역할이나 관리 범위가 바뀌지 않는다.
본 API는 이미 등록된 학교의 권한 신청·이력·검토 화면에 연결했다. 최초 가입과 미등록 학교 접수는 [별도 계약](initial-school-admin-signups.md)에서 계정·학교 정보와 함께 처리한다. 학교 SSO·이메일 소유 인증·자동 교직원 확인은 포함하지 않는다.

### 신청자

prefix는 `/api/v1/me/school-admin-applications`다. 기존 쿠키/Bearer 세션이 필요하다.

| 메서드·경로 | 동작 |
|---|---|
| `POST {prefix}` | 등록된 학교에 본인 신청, 201 |
| `GET {prefix}` | 본인 신청 이력, 상태·학교 필터와 UUID cursor |
| `GET {prefix}/{id}` | 본인 신청 상세 |
| `POST {prefix}/{id}/cancel` | `expected_version`으로 대기 신청 취소 |

생성 입력은 `institution_id`, 재시도 UUID `client_id`, `position`(1~128자),
`contact_email`(정규화 이메일, 최대 254자), `reason`(1~1000자)다. 소속·연락처는
신청자가 입력한 정보이며 검증 결과가 아니다. 학교 선택은 기존 `/catalog/institutions`를
사용한다. owner·역할·상태·승인 플래그 등 추가 필드는 거부한다.

일반 계정과 학교관리자가 신청할 수 있다. 슈퍼관리자는 새로 신청하지 않는다.
이미 해당 학교의 활성 관리 범위가 있거나 같은 학교에 대기 신청이 있으면 409다.
삭제 표시 학교에는 신청할 수 없다. 본인 대기는 최대 5개, 전체 보관 이력은 최대 100개이며
초과는 429다. 본문은 각 필드 길이로 제한하고 프록시의 일반 JSON 요청 한도도 적용한다.

같은 본인/client_id와 정규화된 입력은 기존 신청을 반환한다. 입력이 달라지면 409다.
취소·반려 후에도 같은 키의 재시도는 과거 상태를 반환하며 되살리지 않는다. 보완 신청은
새 client_id로 새 이력을 만든다. 다른 사람의 UUID는 404이며 목록에도 나오지 않는다.

### 슈퍼관리자 검토

prefix는 `/api/v1/admin/school-admin-applications`다. 학교관리자는 이 경로에 접근할 수 없다.

| 메서드·경로 | 동작 |
|---|---|
| `GET {prefix}` | 전체 신청 목록, 상태·학교·cursor 필터 |
| `GET {prefix}/{id}` | 신청과 현재 신청자 계정·권한 버전 |
| `POST {prefix}/{id}/approve` | 확인한 담당자를 승인하고 학교 범위를 부여 |
| `POST {prefix}/{id}/reject` | 대기 신청 반려 |

승인 입력은 `expected_version`, `expected_user_version`, `review_note`(1~500자),
각각 실제 boolean true인 `identity_verified`, `affiliation_verified`다. 슈퍼관리자가
별도 경로로 신원과 해당 학교 담당자 자격을 확인하고 명시적으로 제출하는 기록이다.
시스템이 이메일·학교 소속을 자동 증명했다고 표시하지 않는다. 반려에는 신청 버전과
`review_note`가 필요하다. 이 메모는 신청자에게도 보이므로 내부 비밀을 넣지 않는다.

기존 신원 잠금 안에서 현재 세션·슈퍼관리자 권한·대기 상태·신청 버전·계정 버전을 다시
확인한다. 정지 계정, 슈퍼관리자로 바뀐 신청자, 삭제 표시 학교, 이미 부여된 활성 학교
범위는 승인할 수 없다. 승인 시 **신청 승인·school_admin 역할·학교 전체 범위·권한 버전·
감사 기록을 한 트랜잭션**으로 저장한다. 기존 다른 학교 범위와 개인 자료는 유지한다.
동시 승인·승인/취소 경쟁은 한 번만 성공하며 나머지는 409다. 자신의 신청을 심사하지 않는다.

`pending → approved/rejected/cancelled`만 허용하며 종료된 신청은 수정하지 않는다.
승인 이력의 `granted_scope_id`는 당시 부여한 범위다. 나중에 계정이 정지되거나 범위가
회수돼도 승인 이력을 지우지 않는다. **현재 권한은 `/auth/me`와 각 보호 API가 판단한다.**

모든 목록은 UUID `cursor`, `limit`(1~100, 기본 30), `items/next_cursor`를 사용한다.
응답은 `no-store`이고 오류는 공통 코드·필드 오류·request ID 형식이다. 감사에는 수행자·
신청/범위 ID·학교·행동만 기록하며 연락처·사유·검토 메모를 복제하지 않는다.

`0012_school_admin_applications`는 신청 테이블 하나를 추가한다. 상태/결정 필드 CHECK,
본인/client_id UNIQUE, 본인/학교의 대기 신청 부분 UNIQUE와 FK를 적용한다.
`0013_admin_decision_roundtrip`은 같은 허용 상태를 유지하면서 결정 CHECK의 복원 시
캐스트 표현 차이를 제거한다. 기존 마이그레이션과 백업의 엄격한 비교는 유지한다.
삭제·자동 보관 정리·첨부 증빙·메일 알림·하위 학과 권한은 이 계약의 범위 밖이다.
