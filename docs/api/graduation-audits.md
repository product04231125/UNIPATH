# 학교 검토 자료 기준 졸업요건 감사

## 결과 안내 템플릿

`GET /api/v1/me/graduation-audits/{audit_id}/guidance`는 기존 본인 감사 결과를
`적용 context → 기준일 → 상태·요약 → 요건별 수치·부족 항목·근거 → 추가 확인 사항`으로
안내한다. 별도 계산·LLM 호출·저장은 없다. `requirements`는 각 결과에 해당 규칙의
문서 제목·URL·페이지·버전과 승인 기록의 `source_page`를 연결한다. 상태와 수치는
Rule Engine 결과 그대로다. `issues`, `next_steps`, `notice`로 보완 작업을 안내한다.
`current_usable=false`이면 요약 첫 문장에 재확인을 표시하고 과거 판정은 보존한다.
타인의 감사는 관리자도 404이며 로그인·공통 오류·`no-store`는 기존 감사 API와 같다.

관리자가 검토한 **전체 적용 규정**과 **본인의 학교 발급 승인 기록**을 결정론적인
Rule Engine에 연결한다. 개인 입력·프로필·RAG·LLM을 판정 입력의 대체값으로 쓰지 않는다.
실제 학교의 규정이나 학생 자료를 내장하지 않으며, 학교의 최종 학위 수여 승인을 대신하지 않는다.
Flutter 타입·전송 어댑터와 [감사 화면](../frontend/features/graduation.md),
[자료 제출·기록 검토 화면](../frontend/features/official-records.md)을 제공한다.
전체 적용 규정 검토의 관리자 UI는 별도 작업이다.

## 준비 순서와 권한

1. 학사 메타데이터를 적용하고 [학교 지식](school-knowledge.md)의 출처·본문을 검토한다.
2. [실행 규칙](rule-programs.md)에 숫자·종류·예외를 명시하고 원본 전체 문맥을 승인한다.
3. 아래 관리자 경로에서 학교·학과·교육과정에 적용되는 전체 요건 목록을 확인한다.
4. 학생이 동의해 제출한 [학교 발급 원본](official-record-sources.md)을 검증하고,
   [성적·봉사·자격·논문 기록](official-student-records.md)을 별도로 승인한다.
5. 학생 본인이 문맥·기준일을 지정해 감사를 생성한다. 필요한 규칙·기록은 서버가 선택한다.

문맥은 `institution_id`, `department_id`, `curriculum_id`, `admission_year`, `track`을
모두 요구한다. 실제 학교·학과·교육과정의 소속 관계를 확인한다. 교육과정이 없는 기록이나
다른 문맥의 기록을 임의로 보완·선택하지 않는다. 개인 학업 프로필의 이름·입학연도는 사용하지 않는다.
`as_of`는 필수 `YYYY-MM-DD`이며 미래 날짜는 거부한다. 기록 기준일도 이 날짜와 정확히
같아야 한다. 다른 날짜의 최신 파일을 역사적 기록의 대체값으로 쓰지 않는다.

## 관리자의 전체 규정 검토

prefix는 `/api/v1/admin/graduation-catalog-reviews`다. 슈퍼관리자 또는 해당 학교의
활성 학교 범위 관리자만 접근한다. 범위 회수·학교 삭제 표시는 기존 세션에서도 다시 확인한다.

| 메서드·경로 | 동작 |
|---|---|
| `GET {prefix}/preview` | 위 문맥 5개와 `as_of` query로 전체 적용 목록·문제·정규화 지문을 조회 |
| `POST {prefix}` | 검토한 목록의 명시적 완전성 확인을 불변 스냅샷으로 승인(201) |
| `GET {prefix}` | `institution_id`, `status`, UUID `cursor`, `limit(1..50, 기본 20)`로 이력 헤더 조회 |
| `GET {prefix}/{id}` | 당시 전체 목록·검토 메모와 현재 사용 가능 여부 |
| `GET {prefix}/{id}/events` | 승인·교체·회수 이벤트. 사유는 이 보호 경로에서만 조회 |
| `POST {prefix}/{id}/revoke` | `expected_version`, 비어 있지 않은 `reason`으로 승인 회수 |

생성은 `context`, `as_of`, 재시도 UUID `client_id`, 미리보기의 `expected_catalog_digest`,
`review_note`와 각각 실제 boolean true인 다음 확인을 받는다.

- `all_requirements_reviewed`: 누락 없이 전체 적용 요건을 등록·검토했다.
- `all_levels_reviewed`: 학교 공통·학과·교육과정 계층을 모두 검토했다.
- `sources_reviewed`: 예외·부칙을 포함한 공식 출처와 적용 문맥을 검토했다.

서버는 등록된 목록의 지문이 그대로인지 확인한다. 이는 권한 있는 사람의 검토 확인이며,
서버가 아직 등록되지 않은 학교 규정을 자동 발견하거나 PDF 의미를 증명한다는 뜻이 아니다.
미등록 실행본·모호한 적용본·변경된 출처/마스터·제한 초과가 있으면 승인하지 않는다.
수동 판단 요건은 목록의 일부로 검토할 수 있지만 실제 감사에서 계속 `needs_review`다.
새 공식 경로는 과목·자격/발급처의 검토 당시 버전·코드·이름과 실제 본문 해시도 확인한다.
기존 `/catalog/rule-programs`의 표시 스냅샷과 항상 false인 `catalog_complete` 계약은 유지한다.

문맥 5개와 날짜마다 현재 승인은 하나다. 교체에는 `replaces_review_id`와
`expected_replaced_version`이 함께 필요하며 이전 승인은 `superseded`로 보존한다.
같은 수행자/client_id·요청 지문은 기존 상태의 검토를 반환한다. 내용이 다른 재시도는 409이며,
회수된 검토를 재시도로 되살리지 않는다. 승인 후 원문·조건을 수정/삭제하는 경로는 없다.
범위가 회수된 수행자는 재시도도 할 수 있지만 권한 검사에서 거부된다.

## 학생 본인 감사와 이력

prefix는 `/api/v1/me/graduation-audits`다. 관리자 역할도 이 경로에서는 자신의 자료만 읽는다.
다른 소유자의 UUID는 404이며 다른 학생의 감사 목록·상세를 읽는 관리자 경로는 제공하지 않는다.

| 메서드·경로 | 동작 |
|---|---|
| `POST {prefix}` | 문맥·기준일·재시도 UUID로 감사 생성(201) |
| `GET {prefix}` | 본인 이력 헤더. `institution_id`, UUID `cursor`, `limit(1..50, 기본 20)` |
| `GET {prefix}/{id}` | 불변 결과·조건·근거와 현재 근거의 사용 가능 여부 |

```json
{
  "context": {
    "institution_id": "00000000-0000-4000-8000-000000000001",
    "department_id": "00000000-0000-4000-8000-000000000002",
    "curriculum_id": "00000000-0000-4000-8000-000000000003",
    "admission_year": 2026,
    "track": "single_major"
  },
  "as_of": "2026-10-21",
  "client_id": "00000000-0000-4000-8000-000000000004"
}
```

UUID는 형식 설명용 합성 예시다. 실제 등록된 문맥으로 요청한다. `owner_id`, 직접 입력한
학점/기록 배열, 조건·요건 선택, `catalog_complete` 등 추가 필드는 허용하지 않는다.
현재 신원 잠금 아래 전체 규칙, 승인 검토, 본인 기록을 같은 상태에서 조회하고 이력·감사를
한 트랜잭션으로 저장한다. 원본 철회/규칙 회수와 동시 요청도 이 잠금으로 순서를 정한다.
본인/client_id와 요청이 같으면 과거 결과를 반환하고 현재 사용 가능 여부를 다시 확인한다.
같은 키로 날짜·문맥을 바꾸면 409다. 감사 이력을 수정하거나 삭제하는 API는 없다.

## 결과의 의미와 근거

응답의 `official=true`와 `학교 검토 자료 기준 졸업요건 감사`는 검토한 학교 자료 경로라는
뜻이다. 판정 상태는 `satisfied`, `not_satisfied`, `needs_review`, `not_applicable`이다.
학교 공통 기준만으로 학과·교육과정 요건을 생략하지 않는다. 규칙 목록 전체 검토가 없으면
등록된 세부 요건을 계산할 수 있어도 전체 충족으로 확정하지 않는다.

- `catalog_complete`: 감사 당시 동일 문맥·날짜의 전체 규정 검토 지문이 일치했는지.
- `eligible_as_of`: **감사 당시 그 기준일**에 목록 완전성을 확인하고 요건이 모두 충족됐는지.
- `current_usable`, `current_issues`: 상세 조회 시 그 근거를 지금도 사용할 수 있는지.
  날짜·당시 결과와 함께 확인한다. 이력 목록의 헤더는 과거 상태이며 현재 판정으로 표시하지 않는다.
- `criteria`: 사용한 실행본·규칙의 UUID/버전·명시 조건과 문서 제목·URL·페이지·해시.
  검토 메모·원문 발췌·학생 개인정보를 복제하지 않는다.
- `records`: 본인 승인 묶음·원본 UUID/버전/해시와 데이터 지문.
- `record_evidence`: 계산 근거 기록 UUID를 승인 묶음·묶음 내 client_id·원본 페이지로 연결한다.
- `results`: 요건별 상태·정확한 Decimal 합계·필요량·확정된 부족량·근거 기록 ID.

필요한 기록 종류만 사용한다. 미등록·부분 검토·다른 기준일·회수/철회·변경된 마스터의
기록은 미확인 입력(null)이며, 완전하게 검토한 빈 목록만 `[]`다. 미확인 수치·평점 척도·
자격 유효성·논문 완료를 추정하지 않는다. 재수강을 임의로 합산하거나 문자 성적을 평점으로
환산하지 않으며, 지원하지 않는 학교별 정책은 수동 판단 요건으로 남겨야 한다.

원본 철회·규칙/전체 검토 회수·마스터 변경 후에도 과거 결과·근거·페이지 대응을 바꾸지 않는다.
대신 상세의 `current_usable=false`와 사유를 표시한다. 재계산은 새 client_id로 생성한다.
저장한 최소 입력·조건으로 결과를 다시 계산해 일치 여부와 지문을 검증하며, 손상된 감사는
수치나 원문을 노출하지 않고 공통 503을 반환한다. 원본 PDF나 개인 자유 입력 자료를
감사 JSON에 복제하지 않는다. 일반 감사에는 행동·학교·대상·수행자·request_id만 남긴다.

## 제한과 프론트 계약

생성 요청은 최대 16 KiB이며 양쪽 Nginx에서 감사/검토 경로의 접근 로그를 끈다.
전체 목록은 기존 100개 원본·500개 요건·2000개 근거 한도를 적용한다. 검토 스냅샷과
감사 최소 입력은 각각 최대 4 MiB다. 학교별 검토 이력 1000개, 본인 감사 200개·64 MiB의
MVP 보관 한도를 적용하며 기존 자료를 자동 삭제하지 않는다. DB 백업·격리 복원 범위에 포함된다.

Flutter의 `GraduationCatalogApi.forOwner(auth, currentActorId)`와
`GraduationApi.forOwner(auth, ownerId)`는 현재 로그인에 묶인 전송을 사용한다. 같은 계정의
새 로그인이나 다른 계정 변경 후 이전 capability/응답을 버린다. 본인·단건 ID·생성 문맥/날짜를
확인하며 자동 재시도·로컬 보관은 하지 않는다. 관리자 플래그로 서버 권한을 만들지 않는다.
`backend`에서 `python ../scripts/export_graduation_contracts.py`로 타입을 다시 만들고
생성 파일에 `dart format`을 적용한다. 상세 wire 계약은 [OpenAPI](openapi.json)다.
