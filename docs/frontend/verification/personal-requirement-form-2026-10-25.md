# 학생 졸업요건 폼의 계산 조건 연결 — 2026-10-25

- LocalRecordWorkbench 개인 규칙에 종류별 계산 입력을 삽입했다. 별도 Form으로 요건 설명 저장과 계산 조건 검증을 분리하며
  기존 텍스트 설명을 실행 코드로 해석하지 않는다. 설명은 한 줄, 종류/최소량은 실제 계정에서 같은 행이다.
- 기존 개인 계산 입력 위젯을 분리해 필수 과목의 학점/점수·척도, 자격 보유/유효 관찰, 논문 완료/승인 관찰을 유지했다.
  종류를 바꿔도 폼의 조건 초안을 보존하고 폐기 확인에 포함한다. 자유 현재 값 입력 대신 서버의 현재/필요/부족/상태를 표시한다.
- 개인 규칙 API에는 영속 typed condition 필드가 없다. 요건 설명을 먼저 저장한 뒤 개인 계산 API로 조건과 결과를 저장한다.
  metadata에 임시 필드나 JSON을 끼워 넣지 않는다. 계산 실패 후 요건을 다시 생성하지 않으며 같은 요청을 재사용한다.
- 최신 계산 이력의 조건은 요건 버전이 같은 경우만 복원한다. 필수 과목의 점수/척도 관찰도 복원하며 기록에서 추정하지 않는다.
- 신규 API 어댑터 위젯 회귀: 최소120 전송, 응답 유실 후 동일 요청 재시도, 서버 이력에서 조건 복원, 읽기만으로 POST 없음.
  기존 계산/개인 졸업 CRUD/배치 포함 데스크톱22개 통과. 기존 배치의 숨긴 자유 값 입력 기대와 동일 탭 문구 탐색을 수정했다.
- 초기 테스트 컴파일의 잘못된 TextFormField 속성 탐색을 수정했다. 관련22개 실행의 탭 탐색1건을 정정해 단일 재실행 후,
  종류/수치 한 행 배치를 포함한 최종22개가 통과했다. 초기 명령1회는 제품 루트에서 실행해 테스트 시작 전 종료했다.
- 분석2회: 분리 후 남은 미사용 helper와 신규 조건문 스타일 등10건을 정리한 뒤 문제 없음.
- Web/Windows build 각1회 성공. 좁은 화면은 --name으로 제외했다. 운영 서버 HTTP·네이티브 실기는 미검증이다.
- 세부 로컬 로그: frontend/requirement-student-final-test.log, requirement-personal-analyze.log,
  requirement-student-web.log, requirement-student-windows.log. 다른 계산 화면의 계약/Rule Engine/API는 변경하지 않았다.
