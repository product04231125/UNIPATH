# 포트폴리오·성과·지원 문서

## 현재 구현

화면은 HTML 목업과 같은 세 단계이며 학교 연동 없이 기기 로컬 자료로 사용할 수 있다.

세 단계는 공통 `PageHeader`로 `성과 기록`, `포트폴리오 구성`, `지원 문서` 제목을 표시한다.
탭 행·제목·설명·본문은 동일한 왼쪽 시작선을 사용하고, 탭 행과 헤더 사이는 12px이다.
구성·문서의 추가 버튼은 헤더 아래 같은 시작선에 배치한다. 중복 영어 라벨을 제거하고
읽기 대기·실패에도 제목을 유지하며 기존 개인 자료·로컬 사용 의도·미제출 안내를 보존한다.

1. **성과 기록**: 종류·기간·나의 역할·결과·공개 가능한 링크의 개인 CRUD.
   원본은 기존 `personal_record_repository.dart`의 portfolio 키에 보관한다.
   fixture는 이 단계의 예시이며 구성·문서의 선택 후보에는 포함하지 않는다.
   논문·캡스톤은 선택 필드로 유형·개인 기록 상태·원 성적 표기·직접 확인한 승인일을
   함께 저장한다. 승인일은 실제 날짜 `YYYY-MM-DD`만 허용하며, 빈 값은 미기록이다.
   원 성적은 숫자 환산 없이 그대로 보존한다. 구성 미리보기·명시적 본문 가져오기에도
   해당 값과 `학교 승인 처리 아님` 문구를 포함한다.
2. **포트폴리오 구성**: 여러 구성을 각각 추가·수정·확인 후 삭제한다. 구성 이름·소개와 성과
   선택·위/아래 순서 이동·구성에서 제외를 저장한다. 원본 성과는 복사·변경·연쇄 삭제하지 않는다.
   `나만 보기`가 기본이며 `지원처 제출 검토용`, `공개 검토용`은 실제 권한·게시가 아닌 로컬 사용 의도다.
   공개 검토용 저장은 내용·권한·개인정보·링크를 직접 확인해야 하며 내용·선택·순서 변경 시 확인을 초기화한다.
3. **지원 문서**: 지원처별 문서 이름·지원처·직무·문서 종류(이력서/자기소개서/기타)·본문과
   참고할 개인 경험·성과를 저장한다. 빈 본문 초안부터 시작할 수 있고 직접 작성·수정·삭제한다.
   `선택한 기록을 본문에 가져오기`는 확인 후 현재 기록의 메타데이터를 본문 끝에 추가하며,
   기존 문장을 덮어쓰지 않는다. AI 생성이나 RAG 근거 선택이 아니다.

구성·문서 모두 로컬 미리보기와 사용자가 누른 뒤의 텍스트 복사를 제공한다. 링크 열기는
[외부 링크](external-links.md)를 따른다. 파일 업로드·온라인 게시·지원처 제출은 하지 않는다.

## 저장과 실패·원본 변경

- `portfolio_workspace_repository.dart`는 구성·문서를 원본과 분리해
  `university_path.portfolio_workspace.v1`에 하나의 JSON으로 저장한다. UI는 JSON을 해석하지 않는다.
- 메뉴·단계 재진입과 재시작 뒤 보존한다. 참조는 `portfolio/<로컬 id>` 또는 `experience/<로컬 id>`이며
  서버 FK가 아니다. 구성 후보는 성과만, 지원 문서는 경험·성과를 선택할 수 있다.
- 저장 성공 뒤 목록을 갱신하고 실패 시 작성 값·선택·순서를 유지한다. 읽기 실패 시 원본 저장 내용을
  덮어쓰지 않고 재시도를 제공한다. 삭제 실패 시 초안을 유지하며 삭제 확인에는 원본 보존을 명시한다.
- 원본이 삭제되면 참조를 자동 제거하지 않고 `원본 기록 삭제됨 · 연결 없음`으로 표시한다.
  수정에서 구성 제외로 정리할 수 있다. 지원 문서 본문은 사용자가 편집한 독립 원문이므로
  원본 기록 변경·삭제로 자동 재작성하지 않는다.
- 알 수 없는 사용 의도는 `나만 보기`로 안전하게 표시한다. 새 참조는 실제 개인 기록만 허용한다.

## ERD·계약 경계

- 성과의 메타데이터는 `Experience.details` 및 HTML 목업과 대응하지만, ERD에는 별도 포트폴리오
  구성·지원 문서 엔터티가 없다. 이번 모델은 사용자 소유 로컬 확장이며 서버 DTO/enum이 아니다.
- 사용 의도·사용자 확인은 저작권·공개 권한 인증이나 제출 완료를 뜻하지 않는다. 실제 서버 권한,
  게시·공유 링크, 업로드·내보내기 파일, 삭제 이력·동기화는 별도 OpenAPI·보관 정책이 필요하다.
- AI 문장·목차·순서 제안, 자동 문서 생성과 RAG 연결은 구현하지 않는다.
- 논문·캡스톤 입력은 ERD `ThesisRecord`의 사용자 소유 정보를 성과의 개인 복사본으로
  보관한다. 공식 논문 레코드나 학교 승인 행위가 아니며 서버 enum을 추정하지 않는다.
  기존 성과의 UUID·참조·저장 키는 유지한다. 기존 기록에는 새 선택 필드 입력을 강제하지 않는다.

## 검증

### 논문·캡스톤 입력 보완

- `thesis_record_test.dart` 3개: 기존 성과의 선택 필드 호환, 원 성적·개인 승인일 출처 보존,
  불가능한 날짜 거부와 작성 값 유지, 저장·수정·재마운트·삭제 확인/취소,
  1440×900 및 480×520·200% 글자 확대에서 입력 접근과 overflow 검사.
- 관련 테스트 1회와 최종 전체 테스트 1회(70개 통과), `flutter analyze` 1회 문제 없음,
  `flutter build web`·`flutter build windows` 각각 1회 성공. 실패 재실행 없음.
- Windows 네이티브 실제 화면·DPI·고대비 수동 확인은 수행하지 않았다.

### 구성·지원 문서 구현 당시 검증

- `portfolio_workspace_test.dart` 9개: 구성·문서 분리 저장, 참조·공개 검토 검증, 원본 삭제·
  알 수 없는 사용 의도, 읽기/쓰기 실패, 선택·순서·검토·수정·삭제·재마운트,
  확인 후 본문 추가·기존 문장 보존·복사, 저장 실패 입력 유지, 두 단계의 480×520·200% 글자 확대.
- `flutter test` 전체 67개 통과. 테스트 명령 3회: 관련 테스트 → 화면 갱신 대기 수정 후 실패한
  2개만 재실행 → 최종 전체 검사 1회. 분석은 중괄호 스타일 수정 후 문제 없음(2회).
- `flutter build web`, `flutter build windows`: 각각 1회 성공. Windows 네이티브 화면·DPI·고대비
  수동 실행 확인은 하지 않았다.
