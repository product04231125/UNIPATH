# 웹·Windows UX 기준

이 문서는 UniversityPath AI의 Flutter Web과 Windows 애플리케이션 목업을 검토할 때
쓰는 화면·창·접근성 기준이다. 공식 지침을 우선하며, 제품 사례는 구현 방향을 이해하기
위한 보조 근거로만 사용한다. API, Rule Engine, RAG의 도메인 책임을 바꾸지 않는다.

## 1. 적용 원칙

- 화면의 물리 해상도가 아니라 **사용자가 실제로 확보한 앱 창의 가용 폭**을 기준으로
  반응형 전환을 결정한다. 브라우저를 반 화면에 배치한 경우도 별도 화면 크기로 본다.
- 창을 크게 만들 때 더 많은 정보가 보이고, 작아질 때는 내용이 겹치거나 잘리지 않도록
  재배치·숨김·오버레이를 사용한다. 사용자가 먼저 창 크기를 조절해야만 쓸 수 있는
  화면은 기본 크기가 잘못된 것으로 본다.
- 일반 본문과 목록은 줄바꿈·유동 폭을 우선한다. 열의 상대 위치가 의미인 교육과정
  행렬 표만 가로 스크롤을 허용하며, 그룹 헤더·열 헤더·데이터 행을 같은 스크롤
  컨테이너에 둔다.
- AI는 기록과 규정 확인을 돕는 보조 작업 공간이다. 학점·필수과목·승인 여부의 충족
  판정은 대화가 아닌 Rule Engine 결과로 표시한다.

## 2. UniversityPath 화면·창 규칙

| 대상 | 현재 기준 | UX 의도 |
| --- | --- | --- |
| Windows 메인 창 | 기본 `1440×900`, 최소 `1365×768` | 좌측 탐색, 본문, 우측 AI 패널을 함께 읽을 수 있는 최소 작업 공간을 보장한다. |
| 분리 AI 창 | 폭 `300–480px`, 최소 `300×520` | 짧은 질의를 곁에 두되 본문을 가리지 않는 보조 창으로 유지한다. |
| Web/Windows 본문 | 가용 폭 `1180px` 이상에서 우측 도킹 패널 사용 | 본문과 AI가 나란히 보이는 데스크톱 작업 공간을 제공한다. |
| 좁은 Web 창 | 1180px 미만에서 채팅 아이콘과 오버레이 사용 | 본문 폭을 우선하고, 필요할 때만 AI를 연다. |
| AI 기본 상태 | 닫힘 | AI가 필요한 사용자만 열도록 하며 홈과 기록 화면의 초기 집중도를 유지한다. |

### AI 패널과 분리 창

- 도킹 패널은 드래그로 폭을 바꾸되 `300–480px` 안에서만 조절한다. 본문 폭이 먼저
  침해되지 않도록 한다.
- Windows에서만 AI를 독립 OS 창으로 분리할 수 있다. Web의 같은 동작은 브라우저가
  허용하는 팝업 창이며, 차단될 수 있음을 UI와 오류 상태에서 고려한다.
- 독립 창이 있으면 메인의 채팅 아이콘은 새 창을 만들지 않고 해당 창을 전면화한다.
- 메인을 최대화하면 분리 창은 자동으로 닫고 메인 우측 도킹 패널로 복귀한다. 두 창이
  겹쳐 내용을 가리는 상황을 방지한다. 최대화된 메인에서는 `새 창으로 분리` 동작을
  노출하지 않는다.
- 독립 AI 창은 최대화하지 않는다. 전체 화면 작업은 메인 창과 도킹 패널의 조합으로
  수행한다.

이 방식은 보조 대화를 새 창으로 열어 멀티태스킹하게 하는 Microsoft Teams의 패턴과,
주 작업 공간 반대편에 보조 사이드바를 두고 필요 시 숨기는 VS Code의 패턴을 참고한다.

## 3. 레이아웃과 정보 밀도

### 홈과 기록 화면

- 홈은 일반 데스크톱 높이에서 핵심 행동과 현재 상태가 한 화면에 들어오도록 우선
  압축한다. 카드가 줄어들면 장식·보조 설명·여백 순서로 축소하고 핵심 행동은 남긴다.
- 활동, 경험, 자격, 포트폴리오·성과는 같은 카드 밀도와 그리드 규칙을 사용한다.
  특정 메뉴만 중앙 정렬하거나 다른 폭을 쓰지 않는다.
- 본문은 너무 넓어져 읽기 어려워지지 않도록 제목·설명 블록의 최대 줄 길이를 둔다.
  넓은 QHD 창에서 남는 공간은 카드 간격과 보조 영역에 쓰고, 의미 없는 빈 여백으로
  남기지 않는다.

### 표와 데이터

- 대학 공통·학과 기준·기록 목록 등 일반 표는 가용 폭에 맞춰 열 폭을 재배분하고,
  긴 텍스트는 줄바꿈한다. 필수로 읽어야 하는 텍스트를 말줄임표로만 숨기지 않는다.
- 교육과정 학점 현황처럼 비교 축이 많은 표는 각 셀의 최소 폭을 유지하고 가로
  스크롤을 제공한다. 스크롤 시 상단 묶음(`교양`, `전공`)과 모든 행이 함께 이동해야
  한다.
- 작은 폭에서 행렬 표를 억지로 축소해 글자·상태 배지를 겹치게 만들지 않는다.
  표의 의미를 보존하기 위해 이 경우에만 가로 스크롤을 허용한다.

### 간격과 조작 대상

- 화면의 기본 간격은 4px 단위로 정렬한다. 큰 창에서는 24px 안팎의 본문 여백,
  좁은 폭에서는 12px 안팎의 여백을 기준으로 한다.
- 아이콘만 있는 버튼에는 툴팁·접근 가능한 이름을 제공한다. 마우스뿐 아니라 키보드
  포커스와 터치/펜에서도 쉽게 선택할 수 있는 크기를 유지한다.
- 고정·오버레이된 AI 패널은 현재 키보드 포커스를 완전히 가리지 않아야 하며, 닫기와
  포커스 복귀 수단을 제공한다.

## 4. 접근성 및 반응형 검증

| 시나리오 | 확인 항목 |
| --- | --- |
| Windows `1365×768` | 최소 크기에서 좌측 메뉴, 본문, 도킹 AI가 겹치지 않고 홈의 불필요한 세로 스크롤이 없는지 확인한다. |
| Windows `1440×900`, `1920×1080`, `2560×1440` | 창이 커질수록 본문·표가 확장되고, 정보가 과도하게 늘어나거나 빈 공간만 커지지 않는지 확인한다. |
| 메인 최대화·복원 | 분리 AI가 도킹으로 복귀하고, 최대화 중 분리 버튼이 숨겨지며 복원 시 다시 나타나는지 확인한다. |
| Web 좁은 폭 | 1180px 미만에서 AI가 오버레이로 전환되고 본문이 전체 폭을 쓰는지 확인한다. |
| Web 확대 | 200% 텍스트 확대와 400% 확대에 가까운 좁은 가용 폭에서 일반 본문이 재배치되고, 기능·정보 손실이나 불필요한 2차원 스크롤이 없는지 확인한다. 행렬 표는 의미상 예외로 가로 스크롤을 허용한다. |
| 키보드 | 탭 이동 순서, 열린 AI의 닫기, 닫은 뒤 원래 제어 요소로의 포커스 복귀, 포커스 가림 여부를 확인한다. |

Windows 최소 크기는 레이아웃이 더 이상 쓸 수 없게 되는 지점을 차단하기 위한
프로젝트 정책이다. Web은 창 크기를 강제할 수 없으므로 같은 폭에서 재배치와 오버레이로
기능을 보존해야 한다.

## 5. 근거와 참고 자료

### 공식 지침

- [Microsoft Learn — Windows Layout](https://learn.microsoft.com/en-us/windows/win32/uxguide/vis-layout): 사용 가능한 최소 창 크기 설정, 불필요한 스크롤·데이터 잘림 방지, 창 크기에 따른 정보 확장 원칙.
- [Microsoft Learn — Screen sizes and breakpoints](https://learn.microsoft.com/en-in/windows/apps/design/layout/screen-sizes-and-breakpoints-for-responsive-design): 물리 화면이 아니라 앱 창의 가용 공간을 기준으로 breakpoint를 정하는 원칙과 4px 단위 간격.
- [Microsoft Learn — Responsive layouts](https://learn.microsoft.com/en-gb/windows/apps/develop/ui/layouts-with-xaml): 고정 크기와 유동 크기를 결합하고, 폭에 따라 재배치·숨김·대체하는 방법.
- [W3C WAI — WCAG 2.1 Reflow](https://www.w3.org/WAI/WCAG21/Understanding/reflow): 세로 읽기 콘텐츠는 320 CSS px 상당 폭에서도 정보·기능 손실과 2차원 스크롤을 피해야 한다는 접근성 기준.
- [Flutter — LayoutBuilder and adaptive layouts](https://docs.flutter.dev/learn/pathway/tutorial/adaptive-layout): 가용 제약 조건을 기준으로 큰 화면과 작은 화면의 UI를 전환하는 Flutter 구현 참고.

### 제품 사례

- [Microsoft Teams — Open a chat in a new window](https://support.microsoft.com/en-US/teams/chat/open-a-chat-in-a-new-window-in-microsoft-teams): 주 작업을 유지한 채 대화를 별도 창으로 열고 이동·크기 조절하는 패턴.
- [Visual Studio Code — Custom Layout](https://code.visualstudio.com/docs/configure/custom-layout): 좌·우 보조 사이드바, 패널 표시/숨김, 폭 조절, 좁은 작업 공간에서의 보조 영역 관리 패턴.

참고 자료 확인일: 2026-09-30. 외부 제품의 세부 기능은 그대로 도입하지 않으며,
UniversityPath의 학사·RAG·Rule Engine 책임 분리에 맞는 범위에서만 사용한다.

| 공식 근거 조작 | 문서명, 적용 범위, 페이지, 링크를 한 덩어리로 표시하고 키보드로 열 수 있게 한다. 근거가 없는 경우 출처 모양의 빈 칩을 만들지 않는다. | 답변을 검증하고 학교의 공식 안내로 이동할 수 있다. |

### Windows·Web 완성도

| 항목 | 권장 동작 | 이유 |
| --- | --- | --- |
| 창 상태 기억 | 사용자가 조절한 도킹 패널 폭, 마지막 선택 메뉴, 분리 AI 창의 위치·크기는 다음 실행 때 복원 여부를 선택적으로 검토한다. 화면 밖 위치는 현재 모니터의 작업 영역 안으로 보정한다. | 반복 작업에서 매번 레이아웃을 다시 맞추는 부담을 줄인다. |
| 다중 모니터·팝업 실패 | 분리 창을 열 때 현재 메인 창과 같은 모니터의 오른쪽, 공간이 없으면 왼쪽에 연다. Web 팝업이 차단되면 도킹/오버레이 채팅을 여는 대체 행동을 제공한다. | 새 창이 보이지 않거나 사용자가 찾지 못하는 문제를 줄인다. |
| 창·네트워크 오류 | 창 생성 실패, 네트워크 단절, API 시간 초과에는 사라지는 토스트만 쓰지 말고 다시 시도할 수 있는 인라인 상태를 남긴다. | 학생이 실패 원인과 다음 행동을 알 수 있다. |
| 로딩 성능 | 페이지 전환 시 뼈대 화면을 사용하고, 표·문서 근거는 필요한 시점에 불러온다. 로딩 중에도 이전 기록과 입력 중인 내용은 사라지지 않게 한다. | 대시보드처럼 보이면서도 입력 작업 흐름을 끊지 않는다. |

### 도입 전 확인 질문

- 채팅 폭·열림 상태·마지막 메뉴를 기기 로컬에만 저장할지, 로그인 계정 설정으로
  동기화할지 결정한다. 초기 MVP에서는 개인정보와 동기화 충돌을 피하기 위해 로컬
  저장을 우선 검토한다.
- 포트폴리오 파일의 실제 영구 보관 위치와 삭제 정책은 백엔드·보안 설계가 확정된 뒤
  정한다. 목업에서 파일을 올렸다는 표시만으로 영구 저장을 약속하지 않는다.
- 외부 사이트 결과를 자동 수집하는 기능은 사이트별 API·사용자 동의·학교 승인 절차가
  확인되기 전까지 단순 바로가기와 사용자 확인 입력으로 제한한다.
