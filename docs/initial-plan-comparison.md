# 최초 계획서와 현재 설계의 비교

## 목적과 기준

이 문서는 최초 캡스톤 계획서와 현재 README 및 설계 문서의 차이를 추적한다.
최초 계획서는 당시의 문제 정의와 제출 이력을 보여 주는 기준 문서이므로 수정하지
않는다. 현재 구현 범위와 기술 결정의 기준은 `README.md`와 `docs/` 문서로 삼고,
최초 계획에서 달라진 내용은 이 문서에 기록한다.

> 비교 대상: `캡스톤프로젝트I_계획서(홍요아,이어진,신우철)_.pdf` (2026-09-27),
> `README.md`, `docs/architecture-erd.md`, `docs/database-erd.md`,
> `docs/specialized-ai-and-supporting-tools-proposal.md`,
> `docs/job-matching-decision-layer-proposal.md`

## 핵심 결론

프로젝트의 문제와 MVP의 큰 범위는 유지된다. 현재 문서는 최초 계획을 대체하는
새 기획이 아니라, 다음을 구현 가능한 규칙으로 구체화한 설계다.

- 졸업 판정은 RAG나 LLM이 아닌 결정론적 Rule Engine이 수행한다.
- RAG는 공식 문서의 근거 검색과 출처 반환을 담당하며, 근거가 부족하면 추측하지
  않고 `insufficient_evidence`를 반환한다.
- 채용 비교는 합격 예측이 아니라 구조화된 요건과 후보자 프로필의 설명 가능한
  비교다.
- 외부 AI 호출과 개인화 결과에는 개인정보 최소화, 보유 기간, 삭제 경계를 둔다.

## 현재 문서의 정합성 확인 항목

아래 항목은 설계 의도 자체가 잘못되었다는 뜻이 아니다. 구현 전에 어느 문장을
기준으로 삼을지 결정하고 관련 문서를 같은 변경 단위에서 맞춰야 하는 항목이다.

| 우선순위 | 항목 | 확인된 문서 상태 | 영향 | 권고 결정 |
| --- | --- | --- | --- | --- |
| 해결 | 채용공고 분석의 도입 단계 | 채용공고 수집, 요건 추출, `JobMatch`, `JobMatchDetail`을 모두 2차 MVP로 정렬했다. | 1차 MVP는 학사·자격증·개인화 RAG와 졸업요건 판정에 집중한다. | 2차 API 계약과 파일 입력 정책은 2차 구현 시작 전에 확정한다. |
| 해결 | 논문·캡스톤 요건의 도입 단계 | `GraduationRuleThesis`와 `ThesisRecord`를 1차 MVP 데이터 모델로 이동했다. | 1차 Rule Engine이 학점·자격증뿐 아니라 논문·캡스톤 요건도 판정할 수 있다. | 실제 학과 규정에 따라 졸업시험 등 추가 유형이 필요하면 같은 방식으로 규칙 모델을 확장한다. |
| 해결 | 봉사시간 요건의 도입 단계 | `VolunteerRecord`와 `GraduationRuleVolunteer`를 1차 MVP 데이터 모델로 추가했다. | 학교 시스템 API 없이도 사용자가 확인한 승인 봉사시간과 공식 최소 시간을 Rule Engine으로 비교할 수 있다. | 증빙 파일은 개인 데이터로만 처리하고, 승인 상태가 불명확하면 `needs_review`를 반환한다. |

## 문서 정리 순서 제안

1. 채용공고 PDF 입력의 2차 MVP 포함 여부와 사용자 데이터 저장 경계를 확정한다.
2. Personal RAG의 사용자별 문서 범위·보관 기간·외부 LLM 전송 기준을 확정한다.
3. 1차 및 2차 구현 시작 전에 각 기능의 Pydantic/OpenAPI 계약과 테스트 시나리오를 작성한다.

## 유지 원칙

- 최초 계획 PDF와 HWP는 제출·기획 이력으로 보존하며, 현재 설계에 맞추려고 수정하지 않는다.
- 특정 클라우드, LLM, OCR, 리랭커, 결정형 AI 공급자는 제안 문서에 적힌 것처럼 도입 결정 전까지 확정하지 않는다.
- 문서 간 충돌을 해소할 때도 졸업 판정은 Rule Engine, 공식 근거 검색은 RAG, 자연어 설명은 LLM이라는 역할 분리를 유지한다.
