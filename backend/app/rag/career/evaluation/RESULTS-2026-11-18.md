### 원하는 자연어가 나오는가?

조건별 `explanation`으로 일치/부족/확인 필요 이유가 나온다. 예를 들어 80건 평가 이전의 단일 공고 사전 테스트에서 준비 중 합성 자료를 수성대학교 공고와 비교한 결과는 정보처리기사 미취득 및 정보통신기술자 중급 미보유를 구별하고, 관련 ITQ 자격증은 컴퓨터 관련 자격 우대 근거로 설명했다. 단, 같은 조합의 이번 80건 평가에서는 시간 초과가 발생했으므로 이번 성공 사례로 집계하지 않았다. 합성 자료 전체 자연어 출력은 [results.synthetic.json](results.synthetic.json)에서 확인한다. 실제 PDF 분석 전문은 프로젝트 설명만으로도 재식별될 수 있어 공개하지 않는다. 원본 PDF·분석 전문·실제 공고 원문은 저장소 밖에서 관리한다.

현재 출력은 다음 구조다.

```json
{
  "priority": "required",
  "requirement": "정보처리기사 자격증 보유자",
  "status": "insufficient_evidence",
  "explanation": "제출된 기록에는 취득 준비 중이며 아직 미취득으로 기재되어 있어 보유 근거가 부족합니다."
}
```

위 JSON은 형식 설명용 축약 예시다. 실제 모델 출력·검증에는 공고 인용과 개인 근거 인용이 추가된다. 근거가 부족하다는 말은 항상 실제 미보유를 뜻하지 않는다. 문서에 미취득이 명시된 경우와 자료가 없는 경우를 구별해서 표현해야 한다.

### 우선순위

1. **PDF 인용 안정화:** 문서 추출 단계의 공백/줄바꿈을 일관되게 정규화하고 원문 위치 매핑을 유지하거나, 모델에 짧은 근거 단위를 제공하는 방식을 비교 실험한다. 문구가 바뀐 인용까지 허용하는 방식으로 검증을 풀지 않는다. 이번 측정 중 이 로직은 바꾸지 않았다.
2. **시간 초과:** 공고와 자료를 조건별로 필요한 범위에 한정하는 입력 구조, 호출량과 시간 예산을 비교한다. 원문을 무작정 줄여 자격/경력을 누락시키지 않는다. 이번 테스트의 40초를 단순히 늘려 해결됐다고 볼 수 없다.
3. **공고 내 모순과 짧은 공고:** 본문 학사 이상 vs 표 학력무관 등의 충돌을 별도 확인사항으로 돌려준다. 제목은 프론트엔드인데 본문이 시스템소프트웨어 한 줄인 경우 요구 기술을 추측하지 않는다.
4. **독립 QA:** 프론트·QA 담당자가 공고와 합성 자료를 직접 보고 필수/우대 분류 및 설명의 타당성을 검토한다. 개발자가 만든 합성 사례만으로 평가를 끝내지 않는다.
5. **통합 테스트:** 로그인된 사용자의 DB 자료 선택, 파일 업로드, 개인정보 처리 동의, 실제 `/api/v1/me/job-recommendations`, 오류/시간 초과 UI를 별도로 검증한다. 이 평가에는 DB 저장 자료나 실제 화면을 사용하지 않았다.

## 평가 범위 주의

실제 서비스와 동일한 문서 추출·Gemini 생성·인용 검증 모듈을 사용했지만, 고정 공고를 직접 주입했다. 평가 하네스는 진단을 위해 모델 JSON을 받은 후 동일 `EvidenceAnalyzer` 검증 경로에 넣었다. 앱의 인증·공유 호출 제한·최대 3개 분석·시간 예산은 적용하지 않았다. 프론트/백엔드에 배포하면 80건 결과가 그대로 나온다는 의미가 아니다. 동일 입력이어도 모델 결과는 달라질 수 있다.

공고 20개는 웹/서버/응용 SW/전산 운영 범위의 상세 내용을 검토해 선정한 평가 자료이며, 현재 제목 필터의 자동 검색 결과 20개나 특정 사용자에게 추천할 20개가 아니다. `README.md`의 재실행 명령과 `manifest-2026-11-18.json`을 참고한다.
