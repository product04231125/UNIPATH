# 서버·프론트 적용법 (2026-11-19)

이번 변경은 AI/RAG 코드와 생성 API 명세 문서를 수정한다. 기존 앱 API 라우트를 재사용하며 프론트 화면 코드는 수정하지 않았다. 과거 20개 공고 평가와 현재 운영 한도 10개를 구분한다.

## 서버 적용

1. PR을 develop에 병합한 뒤 최신 API 이미지를 빌드·배포한다. 기존 Vertex/OCR/로그인/DB 설정은 유지한다.
2. API 컨테이너 환경에 `CAREER_SOURCE_MODE=crawl`을 전달한다. 기본값은 `api`이며 서버 설정만 사용한다. 요청의 `source_mode`는 허용하지 않고 422로 거절한다. API 승인 후 `api` 또는 `hybrid`로 복귀할 수 있다.
3. Compose 사용 시 기존 프로젝트명·env 파일·Compose 파일을 유지하고 env 파일에 `CAREER_SOURCE_MODE=crawl`을 넣는다. `compose.yaml`이 이 값을 API 컨테이너에 전달한다(기본 `api`). `compose.server.yaml`과 이미지 ID·자격증명 마운트를 빼지 않는다.
4. 기존 `POST /api/v1/me/job-recommendations`를 사용한다. `keyword`에 쉼표로 최대 5개 직무(총 80자)를 넣는다. `벡엔드`는 `백엔드`로 보정한다. **통합 후보 최대 10개**, LLM 비교는 기존 최대 3개다. 검색어별 최대 3페이지·최대 10개를 모은 후 통합·중복 제거·직무 필터·문서 관련도 정렬로 10개를 유지한다. 전체 네트워크 상세 요청 수가 항상 10회 이하라는 뜻은 아니다.
5. 고용24 직접 공고 필터(`siteClcd=WORK`)와 제목 검색을 사용하고 제목이 직무와 맞는 공고만 상세 조회한다. 직무 동의어 사전은 제한적이다. 외부 연계 공고와 잡코리아·사람인 HTML은 수집하지 않는다.

```json
{
  "keyword": "프론트엔드, 벡엔드, 전산실",
  "region": "전국",
  "academic_stage": "year4",
  "limit": 3,
  "external_processing_consent": true,
  "records": [],
  "documents": [{"filename": "portfolio.pdf", "content_base64": "실제 파일의 base64"}]
}
```

위 예시의 파일 값은 형식 설명용이다. 실제 인증된 학생의 선택 자료와 파일을 사용한다. `academic_stage`는 선택 사항이며 미입력 시 일반 안내다. `year1`, `year2`, `year3`, `year4`, `graduate`만 허용한다. 학년을 나이나 PDF 졸업연도에서 추측하지 않는다. 프론트가 사용자가 확인한 값/프로필 값을 전달한다. 기존 요청은 필드를 생략해도 동작한다.

## 프론트 적용

직무 입력칸은 하나 그대로 둔다. 힌트 문구 예: `프론트엔드, 백엔드, 전산실 (쉼표로 구분)`.

**최종 카드 목록은 `display_candidates`를 사용한다.** 관련 실공고 후보가 있고 수집이 성공하면 최소 1개를 유지한다. 공고 자체가 없거나 수집이 실패한 경우 허구 공고를 생성하지 않으므로 0개일 수 있다.

| `display_type` | 카드 제목/배지 | 설명 |
|---|---|---|
| `evidence_match` | 근거가 확인된 후보 | 선택한 자료와 일치하는 조건이 있음. 지원자격·합격 보장 아님 |
| `closest_needs_review` | 조건 확인 필요 | 일반 추천 조건에 미달하지만 분석된 관련 후보 중 비교상 가까운 1개 |
| `analysis_unavailable` | 분석 미완료 · 검색 후보 | 시간 초과/인용 오류/미설정/예산 소진 등. 역량 부족으로 표현하지 않음 |

각 카드의 `posting`으로 제목·회사·근무지·원문 링크를 표시한다. `analysis_status`, `notice`, `stage_guidance`를 함께 표시한다. 분석 미완료 카드에는 점수나 ‘미확인 필수조건 0개’를 표시하지 않는다. 지원조건의 개수를 판단할 수 없기 때문이다. 세부 비교는 같은 `source` + `source_id`의 `items[].comparisons`를 연결한다.

기존 `recommendations`는 근거 일치 추천만 유지하며 조건 확인 후보를 넣지 않는다. `items`, `closest_candidates`는 호환성을 위해 유지한다. **`recommendations`만 그리면 모델 실패 시 빈 화면이 될 수 있으므로 최소 카드 요구사항에는 `display_candidates` 연결이 필요하다.** 기존 화면에서 자동으로 새 배지가 생기는 것은 아니다. `items[].warnings`에도 조건 확인 필요 문구를 제공한다.

## 학년별 세 문장 안내

`display_candidates[].stage_guidance.sentences` 또는 `items[].stage_guidance.sentences`를 순서대로 출력한다.

1. 현재 자료에서 확인된 수준
2. 공고와의 핵심 격차 (필수조건 우선)
3. 다음 학기·방학에 할 일

1학년은 탐색, 2학년은 진로 후보·첫 경험, 3학년은 부족분 보완, 4학년은 취업 전 핵심 격차, 졸업 후는 지원 전략에 초점을 둔다. 이미 근거가 충분하면 저학년이어도 기초부터 다시 하라고 하지 않는다. 학년만으로 역량을 낮게 평가하지 않는다. 미입력 시 중립적 일정 안내를 사용한다.

팀원의 ‘충격을 주는 안내’는 **근거가 없는 핵심 조건과 준비 우선순위를 분명히 보여주는 방식**으로 반영했다. 취업 불가능, 졸업 불필요, 특정 활동을 하면 취업 보장 같은 문장은 만들지 않는다. 자격증·경력·법적 조건은 보유 여부와 증빙을 먼저 확인한다. 이미 수행한 경험인데 자료가 빠졌다면 새 활동보다 기록 보완이 필요할 수 있다.

`comparison_refs`는 세 문장에 사용한 조건의 `requirement_id`를 연결한다. 모델 실패 시 별도의 판단 보류 문장을 출력한다. 세 문장 생성은 검증된 비교 결과를 사용하는 템플릿이며 LLM 추가 호출이 없다.

## 인수 테스트

- 직무 3개 입력 → `search_keywords` 3개, `candidate_limit=10`, `candidate_count<=10`.
- 정상 비교 → 근거 카드 및 조건별 자연어 설명.
- 모든 조건 부족 → 관련 후보 1개의 조건 확인 필요 카드와 부족한 근거 설명.
- 모델 실패 → 관련 후보 1개의 분석 미완료 카드. 거짓 일치 근거를 생성하지 않음.
- 전산실 냉난방/케이블 공사 → 제외. 직무가 맞는 공고 자체가 없으면 검색어 변경 안내.
- 학년 1~4/졸업/미입력 → 세 문장, 단계별 실행 계획. 충분한 기록은 학년과 무관하게 인정.
- 인증·DB 소유권·자료 버전 재검증·동의·업로드/OCR·프록시·실제 화면은 배포 환경에서 확인.

## PR 통합 검사 후속 작업

2026-11-19 GitHub Actions에서 `test_published_openapi_matches_live_contract` 실패를 확인한 뒤, 잠금 파일의 의존성으로 실제 앱 OpenAPI를 재생성했다. 변경은 RAG 요청 모델의 선택 필드 `academic_stage` 추가이며, 리뷰에 따라 `source_mode`는 제거했다. `docs/api/openapi.json`에 이 생성 결과를 반영했으며 프론트·백엔드 구현 코드는 변경하지 않았다. 배포 및 실제 학생 화면 검증은 별도다.

## PR #77 리뷰 반영

- 실제 PDF 분석 전문과 실제 공고 원문은 저장소 및 PR 브랜치 이력에서 제외한다. 개인 결과는 접근 제한된 저장소 밖 경로에서만 보관한다. 합성 자료 결과와 집계 요약은 유지한다.
- 수집 모드는 서버 `CAREER_SOURCE_MODE`로만 제어한다. 스테이징 Compose 연결은 서버 담당자가 병합 시 적용한다.
- 직접 공고 검색 필터를 사용하지만 외부 연계 공고가 반환돼도 유형과 무관한 상세 링크 유무로 최대 3쪽까지 탐색한다. 직접 공고가 없으면 0건이며 무관한 공고나 외부 본문으로 채우지 않는다. 검색어를 실제 직무명/기술명으로 조정하거나 기존 수동 공고 분석 경로를 이용한다. 공개 페이지 구조와 직접 공고 수에 따라 IT 검색 결과가 적을 수 있다.
- 상세 일부 실패 시 성공 공고를 유지하며 `sources[].status=partial`, `detail_failures={원인코드: 건수}`를 반환한다. 전부 실패 시 `failed`/`not_available`이며 정상 0건과 구분한다. 캐시 적중 시에도 같은 집계가 유지된다. 원문·예외 본문은 로그에 남기지 않는다.
- `recommendations`는 근거 조건을 통과한 추천 전용이다. `closest_needs_review`는 `display_candidates`에만 넣는다. 기존 화면에서 조건 미달 후보가 일반 추천으로 보이지 않으며, 최소 카드 표시는 프론트의 새 필드 연결이 필요하다.
- 검색어 최대 5개가 순차 수집되므로 전체 60초 예산이 소진될 수 있다. 운영에서는 직무 1~3개와 캐시를 활용하고, `budget_exhausted`를 분석 미완료로 표시한다.

리뷰 보완 실측(2026-11-19): `백엔드` / 직접 공고 필터로 공개 수집 5건, 상세 실패 0건, 약 2.5초. 개인 자료와 LLM은 호출하지 않은 수집 단계 검증이며 향후 결과 건수/시간을 보장하지 않는다. 비통합 테스트 461개 및 Ruff 통과.
