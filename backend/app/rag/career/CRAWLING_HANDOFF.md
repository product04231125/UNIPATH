# 채용공고 크롤링 대체 경로 · 서버 / 프론트 인수

기존 사람인·고용24 API와 Greenhouse 코드를 유지한다. 승인 없이 사용하는 대체 경로는 **고용24 공개 HTML의 직접 등록 공고**다. 검색 링크만 반환하지 않고 공고 상세의 직무내용·학력·경력·자격면허·근무지 등을 가져와 기존 Gemini 근거 비교와 추천 생성으로 연결한다. 워크넷은 고용24로 통합되어 별도 공급자로 중복 수집하지 않는다.

잡코리아는 공개 검색 요청에 보안정책 페이지를 반환했고, 사람인 HTML 수집은 이번 변경에 포함하지 않았다. 고용24 목록에 있는 잡코리아 등 외부 연계 공고도 상세 수집하지 않는다. 모든 사이트를 수집하는 구현은 아니다.

## 서버: 화면 변경 없이 전환

업데이트한 API 이미지를 배포하고 API 프로세스 환경에 `CAREER_SOURCE_MODE=crawl`을 전달한다. 수집 모드는 이 서버 설정만 따른다. 기존 인증·동의·문서 OCR·Vertex 설정은 필요하고 채용 사이트 인증키는 필요하지 않다.

로컬에서는 저장소 루트에서:

```sh
CAREER_SOURCE_MODE=crawl docker compose -f compose.yaml up -d --build api
```

`compose.yaml`이 `CAREER_SOURCE_MODE`를 API 컨테이너에 전달한다(기본 `api`). 서버에서는 **현재 사용 중인 프로젝트명·env 파일·Compose 파일 목록을 그대로 유지**하고 env 파일(예: `.env.staging`)에 `CAREER_SOURCE_MODE=crawl`을 넣은 뒤 컨테이너를 다시 만든다. 서버 이미지 ID는 이번 변경을 포함한 이미지로 바꾼다.

| 모드 | 동작 |
|---|---|
| `api` | 기존 동작. 서버 변수가 없으면 이 모드 |
| `crawl` | 고용24 HTML만 사용. 승인 대기 중 권장 |
| `hybrid` | 기존 API/Greenhouse와 HTML을 함께 수집. 동일 고용24 ID는 중복 제거하고 상세 본문을 우선 |

복귀는 API 환경의 `CAREER_SOURCE_MODE=api`로 컨테이너를 재생성한다. 요청 `source_mode`는 허용하지 않는다.

## 프론트: 서버 설정에 따라 기존 요청 사용

`POST /api/v1/me/job-recommendations`의 기존 인증된 본문을 그대로 사용한다. `source_mode`를 보내면 422로 거절한다. `keyword`, `region`, 선택한 `records` 또는 `documents`, `external_processing_consent: true`는 기존 계약과 같다. 예: 직무 `Python`, 지역 `전국`, `limit: 3`. API 키는 브라우저에 전달하지 않는다. 수집 방식은 서버 관리자가 설정한다.

응답의 기존 `items`, `recommendations`, `document_locations`는 유지한다. `sources`의 성공 항목에 `collection_method: "crawl"`이 추가된다. `source`는 계속 `work24`이므로 기존 출처/카드 표시를 재사용한다. `recommendations`에는 근거가 확인된 추천만 포함된다. 조건 확인 후보는 `display_candidates`에만 포함된다. 최소 카드 표시에는 `display_candidates`를 사용한다. `items`는 비교한 후보이며, 추천 0건이면 일치 근거가 부족하다는 의미일 수 있다. 공고 수집 성공을 LLM 성공으로 표시하지 않는다.

- `sources[].status=failed`: `failure_reason` 확인. `crawl_markup_changed`, `crawl_detail_incomplete`는 페이지 구조 변경, `crawl_disallowed`는 robots 제한, `crawl_busy`는 다른 수집이 20초 넘게 끝나지 않아 순서를 받지 못한 경우다. HTTP/네트워크 오류도 기존 코드로 반환한다.
- `items[].analysis_status=failed`: 모델 호출/인용 검증 오류. `failure_reason`을 확인한다.
- `no_results`: 공개 직접 등록 공고가 없거나 지역/마감 필터 후 후보가 없다. 키워드 변경을 안내한다.
- `not_available`: 수집 실패. 허구의 공고나 데모 공고로 대체하지 않는다.

## 속도와 범위

검색어별 최대 3페이지에서 제목이 직무에 해당하는 고용24 직접 공고 최대 10개, 상세 동시 요청 2개, 네트워크 요청당 5초, 같은 키워드 공개 공고 캐시 5분(프로세스당 최대 32개)이다. 여러 사용자가 동시에 찾으면 같은 키워드는 한 번만 수집하고 나머지는 그 수집을 기다렸다가 캐시를 쓴다. 서로 다른 키워드는 프로세스당 동시에 2개까지 수집하며, 순서를 최대 20초 기다린다(2026-11-22, 이전에는 전체 수집 1개·대기 2초라 동시 사용자가 `crawl_busy`로 실패했다). 개인 문서·분석 결과는 이 캐시에 저장하지 않는다. 수집처에는 사용자가 지정한 직무 키워드만 보내며 포트폴리오 본문은 보내지 않는다.

선택 문서의 단어와 공고 본문이 겹치는 후보를 먼저 선정한 뒤 최대 3개를 기존 Gemini 분석기로 비교한다. 이 순서는 취업 확률 점수가 아니다. 필수조건 미확인 항목은 추천에도 표시한다. 전국 검색을 권장하며 특정 지역은 수집한 공고의 근무지 문자열로 필터링하므로 해당 지역 전체 결과를 보장하지 않는다. 마감 시각이 지난 공고를 제외하지만 채용시까지 공고는 원문에서 최종 확인해야 한다.

매번 전체 사이트를 크롤링하지 않으므로 전체 시장 최적 공고를 보장하지 않는다. 사이트 차단·구조 변경·모델 응답 속도에 따라 실패/부분 결과가 있을 수 있다. 상세 공고 파싱/요청 실패는 해당 건만 제외하고 `sources[].detail_failures`에 원인별 건수를 보고한다. 로그인·CAPTCHA·보안 차단 우회는 구현하지 않는다.

## 검증 기록 (2026-11-18)

실제 고용24 `Python` / `전국` 공고와 Vertex `global` / `gemini-3.8-flash`를 사용했다. 학생 개인정보 대신 합성 Python·FastAPI·PyTorch 프로젝트 이력을 입력했다. 수집→3개 공고 비교→근거 기반 추천 3개 반환까지 30.7초가 걸렸다. AI 응용 S/W 연구개발, 응용소프트웨어 개발, IoT 시스템 개발 공고였다. 각각 미확인 필수조건도 포함되므로 합격/지원자격 보장이 아니다. 이 실측은 OCR·인증 API·배포된 학생 화면을 포함하지 않는 서비스 단계 검증이며, 실제 속도와 추천 수는 공고·문서·모델 상태에 따라 달라진다.

## 한 입력칸에서 여러 직무 검색

프론트 텍스트 필드를 추가할 필요가 없다. 기존 `keyword` 문자열에 `프론트엔드, 벡엔드, 전산실`을 보내면 서버가 쉼표(전각 쉼표·줄바꿈 포함)로 분리해 `프론트엔드`, `백엔드`, `전산실`을 각각 검색한다. `벡엔드` 오타를 보정하고 같은 직무는 중복 검색하지 않는다. 공백만으로는 나누지 않으므로 `웹 개발자`는 한 검색어다. 최대 5개, 전체 문자열 80자 제한이며 빈 목록 또는 6개 이상은 요청 오류다.

각 직무에서 수집한 결과의 중복·마감을 제거하고 전체 후보 중 문서와 관련된 최대 3개를 LLM으로 비교한다. 직무별 3개가 아니며, 모든 직무가 최종 결과에 반드시 포함되지는 않는다. 기존 전체 시간 예산을 유지해 느린 공급자가 있으면 일부 검색·분석은 건너뛸 수 있다. `sources[].keyword`로 직무별 성공/실패를 확인하고, `search_keywords`에서 정규화한 검색어, `candidate_count`에서 중복·마감 제거 후 후보 수를 확인한다. 한 직무 수집 실패가 다른 직무의 성공 결과를 삭제하지 않는다. 이 분리는 `api`, `crawl`, `hybrid` 모두에 적용된다.


## 제목 우선 선별 / 최대 10개 후보 / 최소 비교 후보 (추가 변경)

공개 검색 목록에서 **공고 제목**을 먼저 확인한 뒤 상세를 요청한다. 전산실 근무지 언급이나 엑셀 사용만으로 직무 일치로 판단하지 않는다. 프론트엔드는 프론트엔드·웹개발·풀스택, 백엔드는 백엔드·서버개발·웹개발·풀스택, 전산실은 전산담당·정보시스템·시스템운영 등 명시적인 제목 표현을 허용한다. 전산실 냉난방/항온항습/약국/자료입력은 제외한다. 직무를 가르치거나 교육받는 공고(제목에 강사·튜터·교육생·수강생·훈련생·국비과정·국비지원·양성과정)는 검색어가 그런 직무(예: `프론트엔드 강사`)가 아니면 제외한다(2026-11-22, "[재택가능 / 프론트엔드] 국비과정 전문강사 채용"이 프론트엔드 첫 후보로 올라온 문제). 기타 검색어는 제목에 해당 표현이 있어야 한다. 별칭 사전은 제한적이므로 직무가 맞더라도 모호한 제목은 누락될 수 있다.

검색어별 최대 3페이지(페이지당 10개 요청), 제목 일치 직접 등록 공고 최대 10개를 수집한다. 검색어 전체의 중복·마감·직무 필터 후 문서 단어 일치 순으로 **최대 10개 후보**를 유지한다. 10개는 상한이며 관련 공고가 적거나 외부 연계 공고뿐이면 채우지 않는다. LLM 분석은 기존 최대 3개/시간 예산을 유지한다. `candidate_limit=10`, `candidate_count`는 실제 유지 후보 수, `collected_count`는 통합된 상세 수집 공고 수다. 목록 단계 제목 탈락 수는 여기에 포함하지 않는다.

기존 추천 조건을 만족하는 공고가 없으면 제목 직무가 맞고 분석이 완료된 후보 중 미확인 필수조건이 적고 부분 충족 근거가 많은 **1개**를 `display_candidates`에만 남긴다. `display_type=closest_needs_review`, `notice`, 해당 `items[].warnings`에 조건 확인 필요를 명시한다. 이 경우 `recommendations`는 빈 배열로 유지한다. 프론트 담당자는 이 유형을 일반 추천 대신 **조건 확인 필요**로 표시한다. 기존 필드를 유지하므로 파싱은 가능하지만 유형별 배지는 프론트 연동 작업이다.

모델 분석이 전부 실패/미완료이면 검증된 추천을 꾸미지 않고 `closest_candidates`에 제목 일치 후보 1개와 분석 상태를 남긴다. 기존 `items`에도 후보가 유지된다. 프론트에서는 이를 **분석 미완료 검색 후보**로 표시한다. 직무가 맞는 실공고 자체가 없거나 수집이 실패했다면 0개를 반환한다. 무관한 공고로 최소 개수를 채우지 않는다.

### 2026-11-18 실제 PDF 재검증

사용자 제공 14쪽 PDF와 `프론트엔드, 벡엔드, 전산실` / 전국 조건으로 실행했다. 제목 선별 최종 버전에서는 수성대학교 정보통신기술자 공고 1개만 남았고 항온항습기·약국보조·케이블공사는 제외됐다. 당시 최대 20개 수집 설정이었지만 해당 공개 직접 공고 범위에서 20개를 확보하지 못했다. 현재 운영 상한은 10개다. 최종 실행 13.2초, Gemini 인용 검증 실패(`personal_citation`)로 `recommendations`는 비어 있고 `closest_candidates` 및 `items`에 분석 미완료 후보 1개를 유지했다. 앞선 실행에서는 같은 공고의 비교가 완료되었으나 최종 실행의 성공으로 간주하지 않는다. 실제 학생 화면 배포 검증은 포함하지 않았다.

수집 요청에도 고용24 공개 폼의 제목 검색 옵션 `keywordWantedTitle=Y`를 전달한다. 제목만으로 오인할 수 있는 공고는 상세 직무 확인이 추가로 필요하며, 비교 품질 테스트 결과는 [평가 안내](evaluation/README.md)를 참고한다.

리뷰 보완: 목록 요청에 공개 폼의 `siteClcd=WORK` 직접 공고 필터를 추가했다. 다음 페이지 탐색은 VALIDATION뿐 아니라 CWT/CSI/OEW 등 상세 링크 유무로 결정한다. 외부 연계 상세는 수집하지 않으며 직접 공고가 없으면 0건이다. 최신 오류 집계 및 표시 정책은 TEAM_INTEGRATION.md를 따른다.
